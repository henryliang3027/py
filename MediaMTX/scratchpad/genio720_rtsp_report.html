日期 2026-09-10 裝置 Genio 720 (MediaTek) 來源 MediaMTX (Windows) → ffmpeg / c922 webcam 狀態 單路 720p30 即時顯示已驗證
UDP + RTSP 串流已打通 軟解 720p30 即時顯示已驗證 硬解 v4l2h264dec 相容性問題（已知限制，暫不影響進度）

目前用軟體解碼（avdec_h264）已經可以穩定、低延遲地顯示 720p30 的 RTSP 畫面。硬體解碼器在這個即時串流情境下有協商問題，已排查出根因，先列為已知限制，不卡當前進度。

01 / Genio 720 接 RTSP 注意事項

接線之前，這 5 件事最容易出包

1
編碼端色度取樣必須是 4:2:0
Windows 端 ffmpeg 用 -c:v libx264 若不加 -pix_fmt yuv420p，webcam 原始格式會被編成 4:2:2（High 4:2:2 profile），硬體解碼器直接拒收；軟解可以吃，但仍建議統一用 4:2:0，相容性最高、也省頻寬。
2
UDP 低延遲 vs 防火牆
走 protocols=udp 延遲最低，但 RTP／RTCP 是兩個各自動態配發的 UDP port，Windows 跟 Linux 端的防火牆都要放行，實務上最常卡在這裡（收得到 RTP 但連線仍失敗）。
3
GOP / keyframe 間隔
決定 client 中途加入時要等多久才看得到畫面，也決定硬解對「非 keyframe 起始」的容忍度——這次踩到的雷跟這個直接相關。
4
即時串流的 SDP 不帶解析度
跟本機檔案／測試訊號不同，RTSP 的 SDP 只有編碼參數，沒有寬高。部分硬解晶片（含 Genio 的 v4l2h264dec）需要一開始就知道解析度才能正確初始化，這正是本次踩雷的根因（詳見附錄）。
5
解析度／位元率對 CPU 負載的影響
目前 720p30 軟解很輕鬆；但如果未來接更高解析度來源（例如 360° 環景鏡頭，常見 1920×1920 以上），CPU 負擔會明顯上升，需要重新量測。
02 / 跟主管的說法

軟解 vs 硬解，一句話講差異

軟解是「用 CPU 跑解碼程式」，硬解是「用晶片內建的專用電路解碼」。硬解快又省電，但這次遇到的問題正是它「不夠寬容」——遇到不典型的即時串流就直接罷工；軟解比較笨重，但幾乎什麼都吃得下。

目前採用

軟解 Software Decode

avdec_h264（CPU 通用運算）
  • 用 CPU 核心跑解碼演算法，不需要晶片內建硬體配合
  • 相容性、容錯性高：可處理中途加入、caps 協商時機不理想等不規則情況
  • 代價是吃 CPU；多路串流或高解析度時負載會上升
  • 目前 720p30 單路：即時顯示，無延遲堆積
已知限制

硬解 Hardware Decode

v4l2h264dec（晶片內建解碼電路）
  • 用晶片專用影像解碼電路，CPU 幾乎不用，功耗與 CPU 資源留給其他應用
  • 對輸入串流格式／協商時機更敏感，遇到即時 RTSP 這種「一開始不知道解析度」的情境會初始化失敗
  • 此問題根因在驅動／晶片層的協商邏輯，非單純程式邏輯可修，需要更深入排查或回報原廠
結論與建議

現階段不需要急著修硬解

軟解在目前規格（720p30、單路）下已經是即時顯示、沒有延遲落後，功能目標已達成。建議先把硬解相容性問題列為已知技術債，等出現以下任一情況再評估投入排查：

需要同時多路串流，CPU 負載明顯吃緊
串流解析度大幅提升（例如接 360° 環景鏡頭）
CPU 資源需要留給其他應用邏輯（非純顯示用途）
裝置對功耗／散熱有明確限制
